## 3. 规则落点与设计取舍

### 3.1 状态与事件顺序

```text
出站（host → MCP server）
  adapters.mcpRequestMeta(request) / cua-port.buildRequestMeta(request)
        └─ 唯一可信 requestContext 对象
              ├─ 顶层扁平字段（既有，保持不变）
              ├─ "com.zody/request-context" → ctx   ← canonical
              └─ "com.zcode/request-context" → ctx  ← legacy（同引用）

入站（node_repl server）
  MCP _meta ──► readZodyMcpMetaEntry(requestContext pair)
                   ├ absent（both 缺失/单键非法）→ {} → UNTRUSTED_SESSION_KEY
                   ├ accepted（单键 or 双键归一化相等）→ 路由到该 session
                   └ conflict（不等/任一侧非法）→ {} → UNTRUSTED_SESSION_KEY（不扩权）

结果 sideband（node-repl-host → core）
  run.cuaApp / browserScreenshotImageIndices
        └─ 先删伪造的 legacy+canonical 键（含 producer app-associations 两种表示）
        └─ buildZodyMcpDualMetaEntry(pair, value)：两键同引用
              └─ core 读取：readZodyMcpMetaEntry → accepted 才应用；conflict 只丢该字段
```

### 3.2 为什么把 helper 放到 contracts

- 规则唯一入口原则（AGENTS「避免重复状态和多条写入路径」）：三个包（core / node-repl-host / adapters）都需要同一条双键语义；若各写一遍，`conflict` 判定与归一化顺序迟早分叉。
- 契约层镜像符合 spec §1.3 最后一段：R53 在 CLI contracts 公开入口镜像常量与解析器，不反向 import shared 实现。注册表复用 shared 的**类型**（`McpAppsMetaKeyPair`，类型 import 允许），实现完全自写。

### 3.3 冲突处置的取舍

- `requestContext.failClosed = true`：冲突意味着“谁在调用”不可信，唯一安全动作是回落 `{}`/UNTRUSTED，而不是二选一。
- `errorPresentation` / `nodeReplCuaApp` / `target-app-display` / screenshot indices 冲突：只拒绝该字段，**整条工具结果照常保留**（任务卡 :293“拒绝应用该字段但不丢弃整条结果”）。这不是放宽：失败方向一律是“不应用”，没有任何一侧被优先。
- 为什么不用 shared 的 `readMcpAppsMetaEntry`：两个 zod 世代 + CLI 不允许反向依赖实现；行为等价由双侧 fixture/矩阵测试锁定（§5）。
- producer key `zody.cua/app-associations-v1`：producer 包（`@zody/zody-cua`）不在本单元 writeSet，故 canonical 字面值在 `result.ts` 本地登记并注释来源；宿主只负责“不可信就删”，两种表示都要删，否则改名即可绕过丢弃逻辑。

### 5.4 返修：adapters OAuth 用例的 HOME 依赖（审查意见 12 failed）

**现象复现**：审查命令在同一环境失败 12/39。用空合成 HOME 复跑：

```text
ROOT=$(mktemp -d /tmp/z6.XXXXXX); TMPDIR="$ROOT/tmp"; HOME="$ROOT/home"（空目录）
pnpm --dir apps/zody-cli/packages/adapters exec vitest run tests/mcp.test.ts
→ Tests  12 failed | 27 passed (39)
```

**归因**：失败全部是授权事务用例（`exposes pending OAuth authorization URL…`、`only opens OAuth…` 等）。默认 credential store 指向 `~/.zody/v2/credentials.json`；`runMcpInteractiveAuthorization` 在写凭据之前先由 `tryAcquireAuthorizationLease` 对 `<credentialDir>/<prefix>.authz` 调用 `acquireFileLock`，其 `mkdir(lockFile)`（`packages/shared/src/node/atomicFileLock.ts:192`）不创建父目录，空 HOME 下直接 ENOENT。真实 HOME 上 `~/.zody/v2` 已存在，所以日常跑不会暴露。

**不是本单元引入**：把 R53 对 `adapters/src/mcp/index.ts` 与 `adapters/tests/mcp.test.ts` 的改动 `git stash` 后，同样的空合成 HOME 命令得到 `12 failed | 26 passed (38)`（38 为 HEAD 基线用例数）；先在合成 HOME 里 `mkdir -p $HOME/.zody/v2` 再跑 HEAD 代码则 `38 passed`。因此失败是既有 HOME 依赖，与双键改造无关。

**返修内容**：只在 `adapters/tests/mcp.test.ts` 增加文件级 `beforeAll`，对 `join(homedir(), ".zody", "v2")` 做 `mkdir(..., { recursive: true })`（已存在时 no-op）。不切换 HOME、不注入第二个 credential store、不改任何用例断言或生产代码。返修后：

```text
HOME=$ROOT/home（空）pnpm --dir apps/zody-cli/packages/adapters exec vitest run tests/mcp.test.ts
→ Tests  39 passed (39)
```

**未修根因**：`acquireFileLock` 不建父目录导致的“全新 HOME 首次 OAuth 授权失败”是生产缺陷，修复点在 `packages/shared/src/node/atomicFileLock.ts` 或 `apps/zody-cli/packages/adapters/src/mcp/oauth-lease.ts`，两者都不在 R53 锁定 writeSet，本单元不改；已登记于 §8。

## 8. 遗留与风险（如实登记）

1. **嵌套 csp 子集差异（既有，非本轮引入）**：CLI `mcpToolDisplayUiPayloadSchema.csp` 只接受 `connectDomains`/`resourceDomains`（`.strict()`），shared `mcpToolDisplayUiSchema.csp` 接受四类域。CLI 生产端从不写 frame/baseUri，所以现网 fixture 两侧一致；但如果未来有 producer 往 display 写 `frameDomains`，CLI 回放会整块拒绝。本轮按“只锁不改”处理，并在 `mcp-ui-display.test.ts` 显式登记，建议主控评估是否另派同步任务。
