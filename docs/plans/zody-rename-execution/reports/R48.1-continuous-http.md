## 8. 边界、未执行项与存疑

### 8.1 入口① O×N 的“旧客户端”形态（重要限制）

- 已执行：旧代际 wire 级驱动，请求形态取自 R02 旧构建实际行为（不带 `x-zody-generation`、使用 `x-zcode-rpc-host-capability`）；并以“旧 server 接受同一序列（capability 200 + WS open）”作对照，证明该序列是旧端真实接受的形态。
- 未执行：启动 R02 旧 Electron 桌面（`packages/desktop/out`）作为进程级旧客户端。原因：旧桌面连接由 Electron main + Host 的 IPC/UI 流程触发，本单元锁定的入口是 HTTP/WS 层；驱动旧桌面需要桌面 E2E 框架与 UI 自动化，超出本单元 readSet/writeSet 与“只读产品源码”边界。
- 因此 E1-3/E1-6 的 PASS 只覆盖“旧代际 wire 客户端 × 新 server”的代际拒绝与零副作用，不代表“旧桌面进程 × 新 server”已实测。该子项按未验证保留，需主控决定是否并入 R48.1-D/桌面 E2E 或 R48.2-C。

### 8.2 入口② 新客户端形态

真实客户端 agent 仍是生产实现（`connectServerRemote`），但入口② 的 N×N 只验证 stage 包入口与代际/capability 语义，未跑真实客户端业务 RPC（stage 服务是 standalone-server，业务面与本单元断言无关）。如需“新客户端 × stage 包”的业务级证据，应由 L4/L5 单元补齐。

### 8.3 观察项（不判定为缺陷，交对应 owner）

1. `/api/server-info` 响应未设置 `Cache-Control`（本轮 `cacheControl: null`）；客户端 fetch 使用 `cache: "no-store"`（`packages/desktop/src/host/serverRemoteConnection.ts:168`）。spec `specs/zody-rename-http-attachment.md:10` 写的是 “authenticated server-info (no-store)”。是否要求服务端也显式下发 no-store，属 server-info 缓存语义 owner（R48.1-D）判断；本单元不修改。
2. stage 包 ready/server-info 的 `version` 为 `0.0.0-dev`，而 manifest `appVersion` 为 `0.1.0`（`candidate-artifacts/server-cli-dist-release/zcode-server-darwin-arm64/manifest.json`）。这是构建期版本定义差异还是候选构建问题，交 R48.1-E（部署/运行版本验证）与 R48.2-C 核对；本单元只记录实测值。
