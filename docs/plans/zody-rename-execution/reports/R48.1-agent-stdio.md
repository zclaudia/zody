## 1. 结论摘要

1. **同代 L1 正常**：darwin-arm64 与 linux 容器内，新 Host wire × 新 Agent 均完成 `startup/runtimeIdentity`、`runtime/capabilities`、`session/list` 业务，请求/响应 id 与顺序完整，EOF 后自然退出 0 且无残留进程。
2. **L1 没有代际握手，混布在 wire 层并不被拒绝**：旧 Host（R02 desktop 构建）× 新 Agent 在旧 Host 的 bundled 解析路径下会正常建立 stdio 业务（Host 日志有 agent pid、`sendConversationCommandV4 OK`、`manager-dispose` 后 agent exit 0）；新 Host wire × 旧 Agent 同样成功。唯一“业务前拒绝”出现在旧 Host 的**受支持 env 覆盖路径**（`ZCODE_AGENT_SERVER_COMMAND` 指向新 Agent）：旧 Host 以 `Storage preparation failed: unsupported_runtime` 在业务前失败，零 Agent/业务写入。该拒绝是存储准备能力门禁，不是代际协商。
3. **旧 wire 名被可见拒绝且不进入业务**：旧 `__zcodeRpcControl`、`__zcode_rpc_nested_uint8array_v1`、`zcode-hello` 送入新 Agent 均返回 `-32600 Invalid Zody Protocol message`（`unrecognized_keys` 明确列出旧键/旧字段），后续合法请求仍按序成功；反向（`zody-hello` → 旧 Agent）同样可见拒绝。旧 `ZCODE_DATA_BASE_DIR` 不驱动新 Agent，新 `ZODY_DATA_BASE_DIR` 不驱动旧 Agent。
4. 目标单测复跑通过：`packages/services/test/zodyStdioTransport.test.ts`、`...processTree.test.ts`、`packages/server/test/stdioLifecycle.test.ts` 共 3 文件 / 19 passed / 1 skipped，exit 0。

## 3. 方法与隔离

- Host 侧驱动：`output/zody-rename-r48/r48.1-agent-stdio/harness/` 内的 Node 脚本扮演 Host，按真实 LF JSON wire 发送帧；Agent 侧始终是真实产物进程（darwin 直接 spawn；linux 用本地已有 `node:24.14.0-bookworm` 镜像 + `docker run -i`）。
- 隔离：每格 HOME/workspace/TMPDIR/XDG 独立；darwin 的 HOME 位于单元目录，TMPDIR 用 `/tmp/r48.1a-*` 短根（收尾已删除）；网络代理指向 `127.0.0.1:9`（关闭端口），未联网、未拉镜像。L1 全程使用 stdio，未占用分配区间 47000-47099 的任何 TCP 端口。
- 真实旧 Host 形态：把 R02 `packages/desktop`（`out/`、`bundled-agents/`、`package.json`）复制到单元内 `legacy-desktop-copy/`，并补入旧仓 `config/provider/zcode-builtin.json`，再用 Electron 41.0.3 启动副本 `out/main/index.js`；旧 Host 的 `zody-host-local-1` utility 进程实际运行。Agent 由旧 Host 自己 spawn（不是 harness 直连），观察证据来自旧 Host 自身日志、Agent 日志与进程表。未原地运行旧产物。
- 未注入 require 预加载器、未修改旧产物内容。O×N“强制 bundled”格仅把**新** Agent 字节按旧 Host 的路径约定复制到单元目录 `layout/apps/zcode-cli/packages/cli/dist/zcode.cjs`（复制前后 SHA 均为 `db2242ac…`），用于让旧 Host 走其 `--prepare-storage` 能力路径；该形态不是产品默认配置，已单列说明。

## 5. 逐项断言证据

### 5.1 请求/响应关联与顺序

- `NN` / `NO` / `ON` 每格发送 9 条请求（identity、capabilities、6×`session/list`、capabilities），响应 id 序列与发送序列逐项相等（`results/matrix.json` 的 `responseOrder` / `expectedOrder`）。
- linux 两格 6 条请求顺序同样逐项相等。
- 请求关联忽略乱序：`session/list` 六连发均返回同一会话空集，未出现串响应/丢失。

### 5.2 stderr 分离

- 正常格 stdout 行 100% 可解析为 JSON（`stdoutAllJson=true`，`parseErrors=[]`），Agent 正常启动时 stderr 为空。
- 取消格 stderr 收到 `Error: Protocol input closed`，同进程 stdout 仍只有协议帧（0 解析错误），说明诊断走 stderr、不污染协议流。
- 传输层 stderr 分离由目标单测覆盖：`zodyStdioTransport.test.ts:46-102`（stderr 故障不影响协议、EOF 保留尾行）实测通过。

### 5.3 EOF / 取消后的进程树清理

- EOF 自然退出：`NN` 907ms、`NO` 170ms、`ON` 167ms、`NN-env-oldname` 171ms、`ON-env-newname` 173ms，退出码 0；每格退出后按进程组快照复查 `survivors=[]`。
- 取消（EOF 中断未完成请求）：`NN-cancel` 776ms 退出 0，`survivors=[]`。
- SIGTERM：`NN-sigterm` 62ms 退出 143，`survivors=[]`；未用强退伪造“自然退出”，该格按信号终止如实登记。
- 真实旧 Host 收尾：应用收到 SIGTERM 后，旧 Host 日志记录 Agent pid 55285 `code:0 / terminationKind:'expected' / terminationReason:'manager-dispose'`、`cleanup completed`，应用 exit 0；进程组清理复查无残留。
- 传输层“根进程先退出仍回收 detached 后代 / 按 PGID 回收”由 `zodyStdioTransport.test.ts:142-251`、`zodyStdioTransport.processTree.test.ts` 实测通过。

### 5.4 旧 wire 名不进入业务

- 旧 RPC 控制键/二进制包装键：`__zcodeRpcControl`、`__zcode_rpc_nested_uint8array_v1` 被新 Agent 以 `-32600` + `unrecognized_keys` 明确拒绝，未按控制帧/二进制包装解释；后续业务仍按序成功（格 `NN-oldwire`）。
- 旧/新 hello 首帧：`zcode-hello` 与 `zody-hello` 都被对端以 `-32600` 拒绝，且拒绝发生在任何业务请求之前；Agent stdio 不注册 RemoteServer 握手（与 `specs/zody-rename-stdio.md:7`、`specs/zody-rename-runtime-contract.md:35` 一致）。
- 旧 env 名：仅设 `ZCODE_DATA_BASE_DIR` 时新 Agent 不采用（无 probe 目录、写隔离 HOME `.zody`）；仅设 `ZODY_DATA_BASE_DIR` 时旧 Agent 不采用。与 R30“仅旧值不驱动行为”一致。
- provider 产物命名：新 Agent 写 `zody-builtin.json`，旧 Agent 写 `zcode-builtin.json`（内容 SHA 相同）。旧名只出现在旧 Agent 自己的缓存文件名中，未进入新 Agent 的业务路径。

## 6. 关键发现（只回报，不修改）

### 6.1 L1 设计上不存在代际门禁，任务卡的“混布业务前拒绝”在 L1 无法按代际语义满足

- 规格明确 Agent stdio 是独立 LF JSON 协议、不使用 RemoteServer hello/ack，保持既有 schema 与请求关联：`specs/zody-rename-stdio.md:7`、`specs/zody-rename-runtime-contract.md:35`、`docs/plans/zody-rename-execution/contract-map.md:31`。
- 实测：新 wire × 旧 Agent（A02）、旧 Host × 新 Agent 强制 bundled（A04）均正常完成业务，没有 `incompatible-generation`/426/`incompatible-version` 类拒绝。
- 唯一在业务前拒绝的是 A03：旧 Host 的 `ZCODE_AGENT_SERVER_COMMAND` 路径不声明 storage startup 能力，旧 Host 报 `Storage preparation failed: unsupported_runtime`（错误行见 `isolated/oldhost-on-env/result.json` 的 `hostErrorFacts`）。这是旧 Host 对“自定义 Agent 命令”的既有能力门禁，不是代际校验。
- 处置建议（需主控裁决）：要么确认 L1 按规格豁免该断言、把 L1 的“拒绝”理解为 A03 + 旧 wire 名可见拒绝；要么把它登记为任务卡/规格冲突，退回规格 owner 决定是否在 L1 引入代际门禁。本单元不修改产品码。

### 6.2 新 Host 侧真实产物缺口（影响 N 侧形态）

- R48.0 desktop 构建 exit 1，`output/zody-rename-r48/candidate-artifacts/desktop-out` 实测只有 `metadata/` 与 `renderer/`，缺 `main/`、`host/`、`preload/`（`R48.0-baseline.md:110-127`）。
- 因此 N×N / N×O 的 Host 侧只能使用 wire 等价 harness（派发预案 §5 允许）；“新 Desktop Host 进程 → Agent”这一完整进程链未在本单元复跑，属未验证项。

### 6.3 旧 Host 的受支持混合路径在存储准备阶段失败

- 通过旧 Host 自身支持的 `ZCODE_AGENT_SERVER_COMMAND` 指向新 Agent 时，旧 Host 在业务前失败（`unsupported_runtime`），零 Agent 进程、零 `.zody/cli` 写入。这符合“混布不开放业务”的发布要求，但同时说明旧 Host 无法在无布局改造的情况下使用新 Agent。

### 6.4 Agent 对 SIGTERM 采用默认终止（退出 143）

- `NN-sigterm` 观测到 143，无残留；规格要求的是 EOF/取消清理，未要求 Agent 把 SIGTERM 映射为 0/1。仅登记，不判定缺陷。
