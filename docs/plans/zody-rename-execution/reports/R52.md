## 3. 规则落点与设计取舍

### 3.1 入站（资源 `_meta`）

```text
resources/read 选中 HTML 项 ──_meta──┐
                                     ├─ readResourceMetaBoundary
resources/list 同 uri 条目 ─_meta───┘   ├─ normalizeMcpAppResourceMeta（字段归一化，既有语义）
（仅当选中的 HTML 项没有任何声明时）    └─ resolveMcpAppsCspRelaxations（R50）
                                              ├ absent / accepted → meta.cspRelaxations
                                              └ conflict → 可见错误，拒绝整个资源准备
```

- 单键（`zody/csp` 或 legacy `zcode/csp`）按原 schema 归一化；非法视作未声明（不因识别到旧/新键而放宽）。
- 双键归一化相等才接受，返回规范值，不做“新键优先”。
- 双键冲突（不等或任一侧非法）→ `prepareSandbox` 抛出 `PluginUiBridgeError("resource_meta_conflict")`，消息含两侧键名；**不登记沙箱**、不携带 `cspRelaxations`（也不授予权限），并在失败路径撤销已签发实例 lease（与既有 `resource` 阶段失败语义一致）。

### 3.2 冲突为何选择“可见错误 + 拒绝准备”（设计取舍）

R50 spec §2.3/§2.4 要求：冲突由调用边界**呈现可见错误并拒绝应用该字段**，CSP 冲突必须**拒绝整个声明**、绝不合并或取更宽的一侧；同时 §2.4 描述“冲突时回落规范缺省块”。本轮实现按前两点执行，并把“可见”落在唯一可用的通道上：

- 桥契约（`IPluginUiBridgeService`）没有非致命诊断/告警通道，`prepareSandbox` 的失败是插件卡片唯一能看到的用户可见面（控制器 `fail()` → `phase:"error"`）。因此选择抛错，而不是“继续挂载 + 只写日志”。
- 抛出发生在 `registerSandbox` 之前，因此不存在“带着冲突声明挂载”的窗口：放宽为 0、权限为 0，天然满足“不扩权”。
- 与“回落规范缺省块”的关系：本次拒绝的是整个资源准备，阻止了任何合并取宽；如果主控希望“冲突仍挂载、仅回落缺省 CSP”，需要在契约上增加非致命诊断通道（当前契约与严格回包 schema 均无此字段），属于新契约决策，不属 R52 可自行扩张的范围。

若独立验收认为必须“继续挂载 + 可见错误”，请退回本单元并先由主控决定诊断通道的落点。

### 3.3 出站（能力 / hostContext / 结果 `_meta`）

- 能力：`buildMcpAppsExperimentalCapabilities` 是唯一构造点；4 个扩展能力在过渡期各宣告 canonical + legacy 两键，`surface` 的两键引用同一 `{ id }` 对象。
- hostContext：widgetState 初值 `{ ...hostContext, ...buildMcpAppsWidgetStateContextEntries(state) }`，两键同引用；`state` 来自 `deps.getWidgetState()`（唯一 owner），每次端口挂载只读一次；页面回写仍走 `ui/set-widget-state` → `onUpdateWidgetState`（一次请求一次写入）。
- 工具结果 `_meta`：`truncated` 由 `buildMcpAppsTruncatedMeta(bytes)` 从同一 `{ bytes }` 生成两键；与 `widgetMeta` 合并时保留其他键。
