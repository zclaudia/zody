## 4. 特有断言逐条证据

### 4.1 server 首帧严格 schema

- 新 server 首帧（两平台一致）：
  `{"type":"zody-hello","generation":2,"version":"0.1.0","platform":"darwin|linux","arch":"arm64","pid":<正整数>}`。
- harness 按 `packages/shared/src/validation.ts:591-598` 的严格形状校验（字段集合完全相等、`type=zody-hello`、`version/platform/arch` 非空字符串、`pid` 正整数、`generation===2`）：`helloStrictSchema.ok=true`（用例 1-9、11-13，两平台）。
- 旧 server 首帧为 `{"type":"zcode-hello","version":"0.1.0","platform":"darwin|linux","arch":"arm64","pid":…}`，**无 `generation`**，对新严格 schema 校验失败（用例 10，两平台：`helloStrictSchema.ok=false`）。这正是 N×O 拒绝的输入依据。

### 4.2 ack 后同 chunk 移交

- 用例 1：harness 在**一次 write** 中写出 `zody-hello-ack\n` + 一个 SocketProtocol Regular 帧（Promise 请求 `id=4242, channel="harness-probe", method="probe"`）；证据 `observed.ackTextWritten` 同时含 ack 文本与二进制帧。
- 结果：server 进入业务（`stdio mode ready`），stdout 依次出现 `Initialize` 帧（header `[200]`）与 `PromiseError` 帧（header `[202,4242]`，payload `Channel name 'harness-probe' timed out after 1000ms`），stderr 出现 `Unknown channel: harness-probe`。**尾随字节确实交给 RPC 层**，未被握手读缓冲吞掉。
- 反证：用例 3-6、12 同样把 ack 与 RPC 帧写在同一 chunk，但 ack 非法时 server `exit 1`，stdout 无任何帧（`decodedFrames=[]`），stderr 无 `Unknown channel` → 尾随字节未进入 RPC。
- 产品级同语义另由 `packages/server/test/stdioHandshake.test.ts`「admits only after a valid ack and hands the child exact trailing bytes」用例覆盖（§7）。

### 4.3 旧 `zcode-hello` 立即拒绝且不写 ack

- 用例 10（N×O，旧 server 实启）：harness 收到旧首帧后 **173 ms（darwin）/ 219 ms（linux）** 内拒绝（`clientRejectedImmediately`，阈值 <3000 ms），`ackBytesWritten=0`；旧 server 从未收到 ack，在自身 10 s 超时后 `exit 1`（实测 10.2 s / 10.7 s，`Handshake timeout: no hello-ack received within 10s`），`stdio mode ready` 未出现，HOME/data 无写入。
- 说明：此处 client 是契约等价 harness（新 client 产物缺失，见 §6.1）；产品 `performHandshake` 对 `zcode-hello`/缺代际/多字段的"拒绝且不写 ack"由 §7 的 `stdioHandshake.test.ts` 产品单测覆盖（用例名 `rejects incompatible hello without ack`，5 种变体 + 5 种 JSON 非对象）。

### 4.4 SSH banner 跳过保留

- 用例 2（新契约 client）：在子进程 stdout 前注入 `Welcome to Ubuntu 24.04 LTS …` 与 `Last login: …` 两行非 JSON banner，随后正常完成握手（`clientHandshakeOk=true`，server `stdio mode ready`，exit 0）。实现依据 `packages/server/src/remote/handshake.ts:20-23,72-79`：仅跳过 JSON 解析失败的行，JSON 可解析但 schema 不符立即失败。
- 用例 13（**真实旧 client** + 新 server + banner）：旧 client 跳过两行 banner 后继续等待其旧 `zcode-hello`，最终以 `Handshake timeout: no zcode-hello received within timeout` 拒绝，`ackBytesWritten=0`；没有把 banner 当成协议错误。旧 client 的 banner 跳过逻辑见其构建产物 `legacy/host/chunk-VAIEJOVH.js`（只对以 `{` 开头的行做 JSON 解析，其余行忽略）。

### 4.5 取消/EOF 零 admission

| 用例 | 触发 | server 行为 | admission 证据 |
| --- | --- | --- | --- |
| 7 `NN-eof-before-ack` | hello 后 EOF，不写 ack | `fatal: Error: Stream closed before hello-ack`，exit 1（darwin 583 ms / linux 516 ms） | 无 `stdio mode ready`；data 目录为空 |
| 8 `NN-cancel-sigterm` | hello 后 SIGTERM（准入前） | 进程被 SIGTERM 终止（`code=null, signal=SIGTERM`）；准入前尚未注册 lifecycle 钩子 | 无 `stdio mode ready`；data 目录为空；无子进程 |
| 9 `NN-cancel-after-admission` | 合法 ack 后 SIGTERM | `termination signal received, shutting down SIGTERM` → `stdio shutdown completed { exitCode: 1 }`，exit 1 | 准入后由 `packages/server/src/stdio-lifecycle.ts:103-118` 统一收口 |
| 3-6、12 | 非法 ack + 同 chunk RPC | `fatal: Error: Invalid hello-ack: …`，exit 1（darwin 160-169 ms / linux 180-232 ms） | 无 ready、无 RPC 帧、无 `Unknown channel`、data 目录为空 |

所有拒绝格（3-8、10-13）在 `evidence/<platform>/cases/<id>/data` 下的文件快照均为空（`dataAfter=[]`）；仅在准入成功格（1、2、9）出现 `provider_config.json`、`runtime/provider/bundled/zody-builtin.json`、`certs/zody-network-ca.*`。这是"业务零副作用"的正面/反面双向证据。

## 5. 混布双向细节

### 5.1 N×N（同代）

用例 1-2、9：新 server + 新契约 client，双向正常；ack 版本 `0.1.0`、`clientId` 非空、`generation:2` 通过 `helloAckMessageSchema`（`packages/shared/src/validation.ts:600-605`，`.strict()`）。用例 3-6 证明严格 schema 逐项生效（错误文本分别命中 `type`、`generation`、`Unrecognized key: "extra"`）。

### 5.2 O×N（旧 client → 新 server，真实双方）

用例 11、13：真实旧 client（R02 旧 desktop host 构建的 `performHandshake` 导出）对新 server 实跑。旧 client 的 schema 只接受 `zcode-hello`（无 `generation`），收到新 `zody-hello` 后既不写 ack 也不误判为 banner，10 s 后以 `Handshake timeout: no zcode-hello received within timeout` 拒绝；新 server 侧无 ack，10.2-10.8 s 后 `exit 1`（`Handshake timeout: no hello-ack received within timeout`），`stdio mode ready` 未出现，data 目录为空，无子进程/端口残留。

用例 12 补充：把"真实旧 client 会写的 ack 形状"（`{"type":"zcode-hello-ack","version":…,"clientId":…}`，取自旧产物内联 schema）直接喂给新 server：186 ms（darwin）/ 295 ms（linux）内 `Invalid hello-ack: type: Invalid input: expected "zody-hello-ack"; generation: Invalid input: expected 2`，exit 1，零 admission。此格 client 是 harness（构造输入），用于单独隔离"新 server 拒绝旧 ack"这一点。

### 5.3 "真实旧 client"的加载形态

`legacy/host/chunk-VAIEJOVH.js` 是 R02 旧 desktop `out/host` 的真实构建产物，ESM 且可在 Node 中直接加载，导出 `performHandshake`、`wrapStdioStream`（尾部 `export{…At as performHandshake…}`）。本轮只**导入其导出函数**驱动，不修改产物、不注入 require 预加载器、不以源码直跑替代。其 `StdioStream` 契约（`onClose` 为 Event）与旧源码 `packages/server/src/remote/backend.ts` 一致；harness 提供子进程 stdio 适配层并记录 client 实际写出的字节数。

未验证边界：生产形态是 Electron host 进程内的同一函数；本轮验证的是同一构建产物在 Node 下作为协议对端的可执行性（函数级真实、宿主不同），已在 §6 登记。

### 5.4 观察（不作为缺陷）

- 旧 server **不监听 stdin EOF**：`NN` 之外的旧 server 在客户端 EOF 后仍等待 10 s ack 超时（早前 smoke 与用例 10 均复现）。这是旧实现的既有行为，新契约只约束新 server；混布 O×N 时旧端若有 EOF 也可能直到超时才收口。未发现新 server 的同类问题。
- 新 server 在**准入前**收到 SIGTERM 时没有 lifecycle 钩子（`registerStdioProcessLifecycle` 在 ack 之后注册，`packages/server/src/entry-stdio.ts:76-90`），进程由默认信号处理终止。由于此时尚未创建任何 RPC/服务/子进程，零 admission 与资源清理均成立；如未来要求握手期也打印终止日志，可将注册前移，但不应改变"不等待 ack 超时"的拒绝语义。

2. **新 client 产物缺口**：desktop 构建失败导致 `main/`、`host/` 缺失（§6.1）。除 L2 外，任何需要新 desktop host/main 实跑的格（L1 旧 Host 形态、L3 continuous 的桌面端）都会受同一缺口影响，建议主控统一裁决。
3. **R02 旧 server 的 ack schema 非严格**（观察）：旧 bundle 内联 ack schema 未 `.strict()`，多出字段会被静默剥离；旧产物不受新契约约束，仅作为混布输入记录，未修改。
